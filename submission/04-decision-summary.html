Here is what I worked with. The system is an HR-onboarding assistant that lives in Slack or Teams. It guides new hires through their tasks and answers policy questions, so it sits right next to very sensitive HR data. The failure I analysed is a privacy failure. This is the path a request takes: a message arrives in the channel, the orchestrator pulls data from the HR checklist, the document index and its memory, the model writes a reply, and the reply goes back to the channel. Solid boxes are things I know exist. Dashed boxes are where I am assuming: what those stores contain, and who can see the reply. The fact is this: the bot posted a hire's missing visa document in the shared cohort channel, where everyone could read it. Two more leaks are reported but not confirmed: a hire's own address and tax details repeated back, and real employee names and pay showing up in policy answers. A disclosure cannot be undone, so we contained first: private messages only, the document index suspended after a snapshot, and logs locked down.
Here are six possible causes, ranked. The columns are the three symptoms, and the dots show which symptom each cause could explain: a full dot means it likely explains it, a half dot means it could contribute, an empty dot means no link. Ranking is provisional. Number one, the bot's replies go to the channel. It is the only cause I can see directly, because the post is public. But it only explains where the message appeared, not why it contained sensitive details. Number two, the HR API returns the full profile and the raw payload goes into the prompt. That matches the bot repeating addresses and tax details. Number three, the document index holds real employee records. That matches real names and pay in policy answers. Then memory that mixes users, missing per-user authorization, and injected instructions. Those rank lower because nothing points to a specific flaw yet, but a shared channel and an unfiltered drive keep them plausible. I did not list hallucination: the problem is that real data is disclosed, not that data is invented. Evidence so far is one public post. The next test is a trace of one request: where the reply was routed, what the API returned, and what the model was given. That single trace separates most of these causes.
The recommendation is to close the exposure, prove the cause, and only then fix. The decision owner is the Head of People Operations, with Security. Step one, contain: private replies only, and the document index suspended after we snapshot it, so the evidence is preserved. Step two, investigate: trace one request and scan the index for real records, while Security checks who else could have seen the posts. Step three, correct: apply the smallest fix the trace supports. If the API sends the whole profile, we cut the payload down to task name, status and due date. If the index holds real records, we rebuild it from an approved list of general documents. Step four, prevent: this failure becomes a permanent test, with an alert if personal data appears in a reply. We call it recovered when the original case passes and a cross-user test set shows zero leaks. That is a release gate, not proof of safety. One confirmed leak switches the feature off. I deliberately defer enterprise-wide permission syncing and a custom red-team suite: once the corpus is a curated list of general documents, they add cost for little risk reduction. Two findings would change my advice: exposure beyond the channel, which pushes toward pausing everything, or a trace showing a broad service account returning other people's data.
